## 0. 30 秒速览

整个系统的全部复杂度来自三件事，先记住这三件，其余都是细节：

1. **一块驱动板 = 一只手爪 = 一条独立 CAN 总线**。四只手爪就是 4 条总线，**绝不能并联在同一条 CAN 上**（因为它们的 CAN ID 完全相同）。
2. **总线是经典 CAN，不是 CAN FD**：1 Mbit/s、11 位标准帧、8 字节数据。用 CAN FD 模式打开发不出去也收不到。
3. **Hall 计数不是手指角度**。Hall 装在减速箱**输入侧**，只反映电机转了多少；手指实际张到多少度，只能靠机械基准 + `zero` 命令人为定义。这是新手最容易误解的地方。

五步上手路径（后续章节逐步展开）：

```
① 断电接线  →  ② 上电，Linux 里把 can0 开到 1Mbit/s  →  ③ 装 Python 环境
                    →  ④ monitor 看到反馈帧  →  ⑤ jog / seek-open 让它动一下
```

在做完 ④ 之前，**不要**执行任何运动命令。

## 1. 系统总览

### 1.1 硬件链路

```text
   ┌─────────┐   USB    ┌──────────────┐  CANH/CANL/GND  ┌────────────┐  UVW + Hall  ┌──────────┐
   │  上位机  │ ───────> │  CAN 分析仪   │ ──────────────> │  手爪驱动板 │ ───────────> │ 三指手爪  │
   │ (Ubuntu)│          │ (KH X6 等)   │                 │ STM32F103  │              │ 3×BLDC   │
   └─────────┘          └──────────────┘                 └────────────┘              └──────────┘
                                                              ↑ 12V 供电
```

- 一台分析仪可以带多路 CAN（KH-UCANFDX6-Mini 提供 `can0`~`can5`，共 6 路）。
- 一块驱动板控制 **一只** 三指手爪，板上有 3 路电机驱动（M1/M2/M3）和 3 路 Hall 输入。
- 每路电机 = 无刷电机 + 减速箱 + 蜗轮蜗杆 + 欠驱动手指连杆。

### 1.2 四只手爪的默认配置

| 手爪 | 驱动板 | 手爪模组 | CAN 通道 | 固件组号 `--claw-group` | 本地电机 1/2/3 |
|---|---|---|---|---|---|
| claw1 | 板 1 | 模组 1–3 | `can0` | `1` | 模组 1 / 2 / 3 |
| claw2 | 板 2 | 模组 4–6 | `can1` | `2` | 模组 4 / 5 / 6 |
| claw3 | 板 3 | 模组 7–9 | `can2` | `3` | 模组 7 / 8 / 9 |
| claw4 | 板 4 | 模组 10–12 | `can3` | `4` | 模组 10 / 11 / 12 |

> ⚠️ **"模组" ≠ "CAN 节点地址"**。模组号只是机械编号，用来保证接线顺序正确。总线上所有板子默认都用同一个 CAN ID，靠**物理上不同的总线**来区分。所以组号只影响板内 PID/PWM 用哪一行默认值，不影响 CAN ID。

### 1.3 名词表

| 名词 | 含义 | 新手常见误解 |
|---|---|---|
| 驱动板 | STM32F103C8T6 + 3× MS4931 双层板（上层/下层叠装） | 不是"电机驱动器模块"，它自己跑控制环 |
| 模组 | 一个"电机+减速箱+蜗轮蜗杆+手指"的机械单元 | 不是 CAN 地址 |
| 组号 group | 固件编译时选的参数行（1..4），一块板烧一个组 | 不是 CAN 地址 |
| 基地址 base | CAN ID 起点，默认 11 | 不是组号，可被 `id-set` 改 |
| 逻辑角度 | 上位机使用的 0–120°，来自 `zero` 定义的基准 | 不是真实手指张角 |
| Hall 码 | 减速箱输入侧相对计数 | 不是末端位置 |
| `zero` | 把当前位置定义为逻辑 0° | 不是"回原点"，它不找机械限位 |
| `seek-open` | 按固定 PWM 往张开方向推，推到不动就停 | 不会自动设零 |
| `grip` | 按固定 PWM 往闭合方向推，不动了转保持 | **不保证夹住物体** |
| HOLD | 保持状态，需要持续心跳 | 不是"松手" |
| `target_reached` | 位置 PID 是否到达目标 | `grip` 时永远是 0，属正常 |

## 3. 安全须知（动手前必读）

1. **全部断电后再接线**：电脑、分析仪、驱动板、12 V 电源，一个都不能带电。
2. **手爪动作范围内不要放人手的任何部位，也不要放易损物**。三指手爪的夹持力足以夹伤手指。
3. **12 V 是硬性要求**。不要"试试 24 V 转得快一点"。
4. **电源正负极按板上的丝印接，不要凭线缆颜色判断**（这批线束的颜色不统一）。
5. **CANH 对 CANH，CANL 对 CANL，GND 对 GND**，接反了通信直接不通，严重时损坏收发器。
6. **现场必须有急停或能一把拔掉电机电源的开关**。软件 STOP 是"尽力而为"，不是安全回路。
7. 第一次上电时，**先只上 12 V 不上运动命令**，确认没有异常发热、异味、冒烟。
8. 调参时**每次只改一个参数**，记录电流、板温、动作时间。改完不要立刻上大电流。

## 4. 接线

### 4.1 分析仪 → 驱动板

| 分析仪端子 | 驱动板端子 | 说明 |
|---|---|---|
| CANH | CANH | CAN 高线 |
| CANL | CANL | CAN 低线 |
| GND | GND | 公共参考地，**必须接** |

### 4.2 驱动板 → 手爪

严格按板上和线束上的编号对应：

```text
驱动板 M1  / HALL1  ->  手指 1（模组 1、4、7、10）
驱动板 M2  / HALL2  ->  手指 2（模组 2、5、8、11）
驱动板 M3  / HALL3  ->  手指 3（模组 3、6、9、12）
```

接线规则（来自 `补充说明.docx`）：

1. **按模组顺序接线**：模组 1 接 PCB 图上的"电机 1" UVW 和 `GH1.25 5Pin`；模组 2 接电机 2；模组 3 接电机 3；模组 4 接下一块板的电机 1，依此类推。
2. 每个模组上的标签会写明编号；**"单侧只有一指"的那一侧，对应模组 3/6/9/12**（也就是本地电机 3）。
3. 每路**电机线和 Hall 线必须成对保持对应**。M1 的电机线不能配 HALL2 的信号线。
4. 线束颜色不清晰时：**先编号、拍照、记录线序，再通电**。这张照片以后排查故障时会反复用到。

### 4.3 终端电阻

- CAN 总线**两端各需要约 120 Ω** 终端电阻。
- 分析仪和驱动板可能已内置终端，要确认拨码/跳线，**避免出现 3 个或更多终端**（会导致波形畸变、通信不稳）。
- 断电后用万用表测 **CANH 与 CANL 之间**：约 **60 Ω** 表示两端终端都接好了。这是最省事的一次性检查。
- **U11 必须用导线短接**（本批板子出厂已短接）。短接后总线电阻才约为 60 Ω。**测试前先用万用表量一遍**，不要凭"应该已经短接了"。

### 4.4 接线后请拍照留档

- 每块板的 M1/M2/M3 + HALL1/2/3 接线实拍
- 模组标签特写（证明模组编号与通道对应）
- 万用表测 CANH–CANL 电阻的读数
- 12 V 电源正负极接法

这些照片在"手指动错方向""某一路完全不动"时是唯一的判据。

逐条打勾，任何一条不过就不要上电：

- [ ] 所有接插件都插到底、有卡扣的已扣好
- [ ] 12 V 电源正负极方向正确（按板载丝印核对）
- [ ] CAN 三根线（H/L/GND）都接好，H/L 没接反
- [ ] 每个总线的 CANH–CANL 电阻约 60 Ω
- [ ] 手爪动作范围内没有人员手部和易损物
- [ ] 急停 / 断电开关在手边，随时可按

## 6. Linux 侧准备（总线打通）

> 本仓库的 KH 驱动是 `kcan`（DKMS 安装）。**当前状态下设备未插入**，所以下面第一步会失败，属于正常——插上设备再继续。

### 6.1 确认设备被识别

```bash
# 1) USB 是否枚举到分析仪（鲲弘的 VID:PID 是 0c72:0012）
lsusb | grep -i 0c72

# 2) 驱动是否加载
lsmod | grep kcan

# 3) 是否出现 can0~can5
ip -d link show type can
```

三条件都满足后才会看到 `can0`…`can5`。若 `lsusb` 里没有 `0c72:0012`，说明**模块没插好或没插**，后面所有命令都无意义。

### 6.2 配置波特率并打开通道

经典 CAN、1 Mbit/s、**关闭 FD**：

```bash
sudo ip link set can0 type can bitrate 1000000 fd off
sudo ip link set can0 up
ip -details link show can0        # 确认 state UP、bitrate 1000000、fd off
```

四只手爪就依次把 `can0`~`can3` 都打开：

```bash
for c in can0 can1 can2 can3; do
  sudo ip link set $c type can bitrate 1000000 fd off
  sudo ip link set $c up
done
ip -details link show type can | grep -E "can[0-9]|bitrate|state"
```

本仓库还提供了封装工具（源码 `tools/kcanctl.c`，编译到 `build/kcanctl`）：

```bash
./build/kcanctl list                       # 普通用户即可，查看通道状态与波特率
sudo ./build/kcanctl up can0 1000000       # 打开 can0 并设 1Mbps
sudo ./build/kcanctl down can0             # 关闭 can0
```

> ⚠️ 通道 **up 之后不能再改波特率**，必须先 `down`。这是 `ip link` 的规则，不是本项目的限制。
> ⚠️ 本项目**不会**在插 USB 时自动打开所有通道。如果之前装过自动配置规则，需要先卸载（见仓库主 README）。

### 6.3 装 can-utils（收发帧调试必备）

```bash
sudo apt install -y can-utils
```

装完后可用 `candump` / `cansend` / `cangen`。**本机目前没装**，这是第一次上手必做的一步。

### 6.4 被动监听：确认板子在说话

```bash
# 先只收不发，看板子有没有在周期性上报
candump -tz can0
```

驱动板在无人发命令时也会周期性上报：

| ID（默认基址 11） | 周期 | 内容 |
|---|---|---|
| `0x00C` (12) | 20 ms | 三路逻辑位置 |
| `0x00D` (13) | 100 ms | 状态/故障/结果 |
| `0x00E` (14) | 20 ms | Hall 码、PWM、计数 |

**看到这三组 ID 才算总线通了。** 按 `Ctrl+C` 停止。

只收 100 帧就自动退出（避免刷屏）：

```bash
candump -tz -n 100 can0
```

### 6.5 一条帧都收不到时的排查顺序

按这个顺序查，**不要跳步**：

1. `ip -details link show can0` 里 `state` 是不是 `UP`？波特率是不是 `1000000`？
2. 12 V 电源是否真的加到了驱动板？（万用表量板上的电源端子）
3. 驱动板有没有上电指示？（LED / 板上 3.3 V 是否正常）
4. CANH/CANL 有没有接反？GND 是否接好？
5. CANH–CANL 电阻是否约 60 Ω？（终端电阻缺失或过多都会失败）
6. 是否用了 **CAN FD 模式**？`fd off` 是必须的。
7. 板子的基址是否被改过？如果别人用 `id-set` 改过，帧 ID 就不是 11–16 了。用 `candump -tz can0` 全量看有没有**任何**帧（不过滤）。

## 8. 第一条命令：`monitor`

**只读，不会让手爪动。** 新手第一条命令永远是它。

```bash
python -m host_demo.claw_demo \
  --interface socketcan --channel can0 \
  --bitrate 1000000 --claw-group 1 --can-base 11 \
  monitor --duration 3
```

典型输出（`state` 可能是 `IDLE`/`MOVING`/`HOLD`/`FAULT`）：

```text
position state=IDLE   deg=[   0.00,    0.00,    0.00]
status   state=IDLE   result=OK      fault=0x00 sync=0.00deg cmd_age=0ms
diagnostic hall=(2, 5, 3) duty_permille=(0, 0, 0) counter=42
FAULT    state=IDLE   result=OK      fault=0x00 sync=0.00deg cmd_age=0ms
```

各字段含义：

| 字段 | 含义 | 怎么用 |
|---|---|---|
| `position deg=[a1,a2,a3]` | 三路逻辑角度（单位 0.01° 解码后） | 只在 `zero` 之后才有物理意义 |
| `state` | `IDLE` 空闲 / `MOVING` 运动中 / `HOLD` 保持 / `FAULT` 故障 | 看到 `FAULT` 先 `clear` |
| `result` | `OK` / `BUSY` / `FAULT` / `RANGE` / `INVALID` | `RANGE` = 目标超范围 |
| `fault` | 故障位掩码，见下表 | 非 0 必须查第 15 章 |
| `sync` | 三路同步误差（度） | 超过阈值会置故障 |
| `cmd_age` | 距上次收到命令的时间，单位 10 ms | **> 500 ms 会关输出** |
| `hall=(...)` | 三路 Hall **状态码**（取值 0–5 的换相码，不是累计计数） | 判断"这一路到底有没有转"的依据：值在变 = 在转 |
| `duty_permille` | 三路 PWM 千分比 | 有目标但 duty=0 → 输出被关掉了 |
| `counter` | 诊断帧计数器 | 用来确认诊断帧在正常刷新 |

**只有 `hall` 会变、`duty` 有值，才说明电机真的在动。**

### 8.1 `fault` 位定义（`App/Inc/claw_control.h`）

| 位 | 值 | 含义 | 处理 |
|---|---:|---|---|
| bit0 | `0x01` | 电机 1 故障 | 断电查该路电机/Hall 线，再 `clear` |
| bit1 | `0x02` | 电机 2 故障 | 同上 |
| bit2 | `0x04` | 电机 3 故障 | 同上 |
| bit3–bit5 | `0x08`–`0x20` | 未定义（固件未使用） | 若出现说明固件版本与本文不一致 |
| bit6 | `0x40` | 三路同步超限（150 counts / 2000 ms） | 重新 `seek-open` + `zero`；查机械是否打滑 |
| bit7 | `0x80` | 通信超时（500 ms 无命令）**或** CAN 板级故障 | 检查上位机心跳；查 CAN 接线 |

> `0x80` 是新手最常见的一位。**上位机崩溃 / Ctrl+C / 拔线** 都会让它置位，手爪随即关输出。这不是板子坏了。

## 9. 动作命令阶梯（由安全到危险）

**严格按这个顺序做**，每一步确认没问题再进下一步。

### 9.1 第 0 级：`jog` —— 单次点动（最安全）

```bash
python -m host_demo.claw_demo --channel can0 --claw-group 1 \
  jog --dir 0 1
```

- 固定 **200‰ PWM、200 ms** 的脉冲，只让一个电机"抖一下"。
- `--dir {0,1}` 是**原始 DIR 电平**，此刻还没标定成"张开/闭合"，两个都试一下，记住哪个方向是张开。
- 参数 `1` 是本地电机号（1/2/3），对应模组 1/2/3（组 1）。
- 用途：验证接线方向、Hall 是否真的在计数、电机线有没有接错。
- 判读：`hall` 状态码应该变化；完全不变 → 电机线或 Hall 线有问题。

### 9.2 第 1 级：`seek-open` —— 往张开方向推到底

```bash
python -m host_demo.claw_demo --channel can0 --claw-group 1 seek-open
python -m host_demo.claw_demo --channel can0 --claw-group 1 seek-open 2   # 只推电机 2
```

- 按各路 `seek_pwm` 向**张开方向**运行，**连续 500 ms 无有效 Hall 变化就停**，三路都停了结束。
- 总期限 5000 ms。
- **它不会自动设零**（`seek` 停滞 ≠ 机械零位）。
- 判读：手指应该张开到机械限位。若某一路不动，单独用 `jog` 查那一路。

### 9.3 第 2 级：`zero` —— 建立逻辑零点

```bash
python -m host_demo.claw_demo --channel can0 --claw-group 1 zero
```

- 把**当前位置**定义为三路逻辑 0°。
- **前提：必须先用 `seek-open` 把手指推到完全张开的机械基准**，并且**人工目视确认**确实是张开的极限位置。
- **不要**在手指半张、卡住、或顶到物体时执行 `zero`，否则后面所有角度都是错的。
- 逻辑范围 **0–120°**（`0`–`120000` 毫度）。0° = 张开基准，120° = 最大闭合。
- `zero` 结果**不写入 Flash**，断电丢失，每次上电要重新做（或由上位机程序每次上电先 `seek-open` + `zero`）。

### 9.4 第 3 级：`open` / `move` / `relative` —— 位置控制

```bash
# 开到逻辑 0°（完全张开）
python -m host_demo.claw_demo --channel can0 --claw-group 1 open

# 走到 60°
python -m host_demo.claw_demo --channel can0 --claw-group 1 move 60

# 走 30°（相对当前位置）
python -m host_demo.claw_demo --channel can0 --claw-group 1 relative 30

# 单指：f1/f2/f3 只动一路；motor 指定电机号
python -m host_demo.claw_demo --channel can0 --claw-group 1 f2 90
python -m host_demo.claw_demo --channel can0 --claw-group 1 motor 2 90
python -m host_demo.claw_demo --channel can0 --claw-group 1 motor 2 90 --speed 8
```

选项：

| 选项 | 默认 | 说明 |
|---|---|---|
| `--speed` | `4.0` | 名义 Hall 轨迹速率，单位 **rpm**；允许范围 **4.0–17.0**，`0` 表示用固件默认（40 drpm）。**不是末端实测速度** |
| `--timeout` | `20.0` 秒 | 超时会自动发 STOP |
| `--clear` | 关 | 运动前先清故障（同一连接内） |
| `--relative` | 关 | `f1/f2/f3` 上把角度当作增量 |

判读：`state` 从 `MOVING` → `HOLD`，`result=OK`，`target_reached=1`，`sync` 不超阈值。

失败常见原因：`result=RANGE`（角度超 0–120）、`fault` 非 0（先 `clear`）、`hall` 不动（机械卡死或线接错）。

### 9.5 第 4 级：`grip` —— 闭合 / 夹持

```bash
python -m host_demo.claw_demo --channel can0 --claw-group 1 grip
```

- 不带角度。三路各自按 `grip_pwm` 往**闭合方向**运行。
- 某一路**连续 500 ms 无 Hall 变化** → 该路转入 `hold_pwm` 保持。
- 三路都转入 HOLD 后，命令返回，并持续发心跳。
- **`target_reached` 永远是 0，这是正常的**，不代表失败。`grip` 的语义是"推到不动为止"，不是"到达某个角度"。
- ⚠️ **`grip` 不代表"夹牢了"。** 它只保证电机推到头并保持一个固定 PWM。夹持力大小 = `hold_pwm` 的大小，与物体是否滑脱无关。
- HOLD 期间每约 1 s 插入一次 20 ms 的 0% EN 脉冲，试图复位 MS4931 的 CLD 堵转计时——**这不是"绕过保护"**。

### 9.6 第 5 级：`run-in` —— 跑合（最危险）

```bash
python -m host_demo.claw_demo --channel can0 --claw-group 1 \
  run-in all --dir 0 --minutes 20 --confirm
```

- **1000‰（满占空比）连续运行**，用于磨合减速箱/蜗轮蜗杆。
- 必须显式加 `--confirm`，否则拒绝执行。
- `--minutes 0` = 一直跑到 `stop` 或 Ctrl+C。
- 期间上位机必须每 200 ms 发心跳；**超过 500 ms 没命令自动停机**。STOP、Hall 故障、CAN 故障、通信超时都会关输出。
- ⚠️ 跑合会产生明显温升和噪音。**必须有人在旁边盯着**，并准备随时断电。先短时间（1–2 分钟）试，确认温升可接受再加时长。

### 9.7 随时可用的三条命令

```bash
python -m host_demo.claw_demo --channel can0 --claw-group 1 stop    # 立即停，关输出
python -m host_demo.claw_demo --channel can0 --claw-group 1 clear   # 清故障锁存
python -m host_demo.claw_demo --channel can0 --claw-group 1 monitor # 看状态
```

`stop` 之后如果需要继续动，要重新发运动命令（`stop` 会清掉目标）。

## 10. 协议细节（想自己写代码时看这一章）

### 10.1 总线与 ID

- Classical CAN 2.0A、11 位标准帧、**1 000 000 bit/s**、DLC=8、小端序、**CAN FD 关闭**。
- 基地址默认 **11**，允许范围 **11–120**。六个 ID 依次是 base+0 … base+5：

| 偏移 | ID（默认） | 方向 | 周期 | 内容 |
|---|---|---|---|---|
| +0 | `0x00B` (11) | 上位机 → 板 | 命令 / 心跳 | 命令帧 |
| +1 | `0x00C` (12) | 板 → 上位机 | 20 ms | 三路逻辑位置 |
| +2 | `0x00D` (13) | 板 → 上位机 | 100 ms | 状态、故障、结果 |
| +3 | `0x00E` (14) | 板 → 上位机 | 20 ms | Hall 码、PWM、计数 |
| +4 | `0x00F` (15) | 板 → 上位机 | 参数应答 | 参数读写应答 |
| +5 | `0x010` (16) | 板 → 上位机 | 故障时立即发 | 故障帧 |

- 基地址存在 STM32 Flash 的 `0x0800FC00`（magic `0x43414E49` + base + `~base`），通过 `id-set` 修改。
- 板的 CAN 滤波器只接受 `base+0` 一个 ID，所以**命令必须发到基准 ID**。

### 10.2 命令帧 `base+0`（8 字节）

| Byte | 内容 |
|---:|---|
| 0 | 协议版本 `1` |
| 1 | sequence（0–255 循环） |
| 2 | opcode |
| 3 | flags 或参数 ID |
| 4–5 | 目标角度（0.01°）或参数值，int16 小端 |
| 6 | speed（drpm，位置命令）/ 电机号 / 掩码 |
| 7 | CRC-8/SAE-J1850（对 byte 0–6 计算） |

位置命令的 flags：

- `0x01` = **相对**移动（相对当前位置的均值）
- `0x00` = 绝对

### 10.3 Opcode 表

| Opcode | 名称 | 说明 |
|---:|---|---|
| `0x01` | SET_TARGET | 三指绝对/相对位置 |
| `0x02` | STOP | 停，关输出 |
| `0x03` | CLEAR_FAULT | 清故障 |
| `0x04` | SET_ZERO | 当前位设为逻辑 0 |
| `0x05` | HEARTBEAT | 心跳，200 ms 一次 |
| `0x06/07/08` | TARGET_M1/M2/M3 | 单指位置 |
| `0x09` | JOG | 固定 200‰ / 200 ms 点动 |
| `0x0A` | SEEK_OPEN | Byte6 = 0 全指 / 1–3 单指 |
| `0x0B` | PARAM_SET | 写参数 |
| `0x0C` | PARAM_GET | 读参数 |
| `0x0D` | GRIP | 三指 PWM 闭合 |
| `0x0E` | RUN_IN | Byte3 bit0 = DIR，Byte6 = 电机掩码（0=三路,1,2,4） |
| `0x0F` | SET_CAN_ID | 改基地址并存 Flash |

### 10.4 反馈帧解析

- **位置 `base+1`**：`byte[1] = state`，`byte[2..7]` 为三路 `int16`，单位 0.01°（即值 ÷ 100 = 度）。
- **状态/故障 `base+2` / `base+5`**：`byte[1] = sequence`、`byte[2] = state`、`byte[3] = fault_mask`、`int16 sync_err`（byte 4–5）、`cmd_age = byte[6] × 10 ms`、`result = byte[7] & 0x0F`、`target_reached = byte[7] & 0x80`。
- **诊断 `base+3`**：Hall 码在 byte 1–3（每字节一个 0–5 的 Hall 状态码，**不是计数值**），`duty = byte[4..6] × 4`（‰），`byte[7]` = 计数器。

### 10.5 状态与结果

| 状态 | 值 | 含义 |
|---|---:|---|
| `IDLE` | 0 | 空闲，无目标 |
| `MOVING` | 1 | 位置环运行中 |
| `HOLD` | 2 | 保持（含 grip 后的保持） |
| `FAULT` | 3 | 故障锁存，需 `clear` |

| 结果 | 值 | 含义 |
|---|---:|---|
| `OK` | 0 | 成功 |
| `BUSY` | 1 | 忙/拒收 |
| `FAULT` | 2 | 有故障 |
| `RANGE` | 3 | 超范围 |
| `INVALID` | 4 | 命令非法（opcode/flags/CRC） |

### 10.6 关键时间常数（`App/Inc/claw_config.h`）

| 项目 | 值 |
|---|---:|
| 控制环周期 | 10 ms |
| 位置反馈周期 | 20 ms |
| 状态反馈周期 | 100 ms |
| 诊断反馈周期 | 20 ms |
| 心跳周期（上位机） | 200 ms |
| **通信看门狗（超时关输出）** | **500 ms** |
| HOLD 期间 CLD 复位 | 每 1000 ms 一次，20 ms 脉冲 |
| 堵转判定 | 800 ms |
| 移动总期限 | 15000 ms |
| seek 无进展 / 总期限 | 500 ms / 5000 ms |
| jog | 200‰ × 200 ms |
| run-in 占空比 | 1000‰ |
| DIR 换向稳定 / 静默 | 20 ms / 300 ms |
| 同步故障阈值 | 150 counts / 2000 ms |
| PWM 周期 | 3600 ticks（20 kHz） |
| 位置范围 | 0–120000 毫度（0–120°） |
| 未设零时的允许范围 | −30000 起 |

> **500 ms 看门狗是最重要的数字。** 你自己写上位机时，必须持续发心跳；一旦程序卡住超过 500 ms，手爪会直接关输出（掉下来，不是保持住）。

## 11. 参数体系

### 11.1 参数写入规则

- 参数写在 **RAM**，**不写 Flash**。**板子重启后恢复固件默认值**，需要重新 `load` 文件。
- **运动或 HOLD 中拒绝写参数**（会返回忙）。
- `set` 之后会**回读校验**；`save` 会完整回读板卡再写文件。
- 参数文件**不保存逻辑零点**。零点每次上电要重建。
- 加载文件前会**校验文件组号与固件组号一致**，不一致直接拒绝。

## 12. 标定流程

标定字面意思：把"电机转了多少"翻译成"手指张了多少"。因为 Hall 在减速箱**输入侧**，这个翻译只能靠人为定义两个端点。

### 12.1 标准流程

```text
① 目视确认手指完全张开（必要时手动辅助）——这是机械基准
② seek-open            推到张开方向到底（500ms 无进展就停）
③ 人工再确认一次：确实是张开的极限，且没有顶到物体
④ zero                 把这里定义为逻辑 0°
⑤ move 60              让它走到 60°，量一下实际张角，记录误差
⑥ 重复 ⑤ 在 30/60/90/120 几个点，做一张"逻辑角 → 实际角"对照表
```

### 12.2 必须知道的现实

- **逻辑角与真实手指角度不是线性关系**，也**不是 1:1**。欠驱动机构在不同张角下的传动比是变的。
- 所以 `move 60` 不保证手指张三指都是 60°。它保证的是"Hall 计数到了某个值"。
- 需要精确角度控制时，只能靠 12.1 第 ⑥ 步的对照表做查表修正，或者加外部传感器。
- 三个手指之间可以不同步（同步误差超过 150 counts / 2000 ms 会置故障位，但这只是粗保护）。

### 12.3 调参原则

- **一次只改一个参数**，改完立刻观察：电源电流、板温、动作时间、机械声音。
- 顺序建议：先 `max_pwm` 给足（否则没劲）→ 再 `kp` → 再 `ki`（注意积分饱和，配合 `integral_limit`）→ 最后微调 `startup_pwm/startup_ms` 解决起步滞后。
- `kd` 默认 0，**不要轻易加**，Hall 计数有量化噪声，微分会放大它。
- `hold_pwm` 决定夹持力。从小往大加，加到能夹住目标物体且不过热为止。
- 每次调完 `params save` 存文件，文件名带上日期和手爪号。**板子重启会丢参数。**

## 13. 接入腿臂工程

### 13.1 现状

- 腿臂侧代码：`examples/walk_control_V1.cpp`（已提交，`0x141–0x144` = 腿 1–4，心跳 `0x161`，回复 `0x41`）。
- 手爪侧：`Hands_ctl_1110/资料/总线驱动软件/claws_control_1/`。
- **两侧尚未合并，也没有做过联合实机验证**（`docs/INTEGRATION.md` 明确写了这一点）。

### 13.2 合并五原则

1. **封装成独立 `ClawModule`**，不要把手爪逻辑塞进关节模块。
2. **共享 socket 时必须统一接收再按 ID 分发**。`python-can` 和 SocketCAN 都是"一条总线一个 socket"，两个线程各 recv 会互相抢帧。正确做法：一个收线程把帧投递到队列，腿臂和手爪各自从队列按 ID 取。
3. **手爪目标不得复用关节载荷字段**。腿臂的关节帧里有位置/速度/力矩语义，手爪是 `(角度, 速度, flags)`，混用会导致解析错位。
4. **通道映射以实际 Linux 接口为准**，不要在代码里写死 `can0`。
5. **板子是经典 CAN**，KH 模块支持 FD 但手爪板不支持。同一个 socket 上不要开 FD。

### 13.3 ID 隔离

- 腿臂用 `0x141–0x144` / `0x161` / `0x41`。
- 手爪用 `base+0 … base+5`，默认 base=11 → `0x0B`–`0x10`。
- 固件注释里明确写了 "TiHu joint nodes remain in `0x001..0x07F`"，即手爪侧的 11–16 落在腿臂的**低 ID 段**，两者数值不重叠，但**如果以后把 base 改到 0x141 附近就会撞**。改 base 前先查腿臂 ID 表。

### 13.4 通道数量问题（必须先解决）

| 用途 | 需要通道 |
|---|---|
| 腿 1–4 | `can0`–`can3` |
| 手爪 1–4 | `can4`–`can7` |
| **合计** | **8 路** |

KH-UCANFDX6-Mini 只有 **6 路**。所以四腿 + 四爪跑不起来。可选方案：

- **方案 A（推荐先做）**：先只接 1–2 只手爪，把 `walk_control_V1` 里腿的通道错开，腾出 `can4/can5`。验证流程跑通再扩。
- **方案 B**：插第二块 KH 模块（通道数翻倍）。注意两块模块同时插入后接口名不一定是顺序的 `can6–can11`，需要按仓库主 README 的「通道绑定」章节用 udev 规则或设备 ID 固定映射，否则每次拔插接口名可能变。
- **方案 C**：手爪用创芯 USBCANFD，腿臂继续用 KH。上位机需要同时开两个 python-can 实例（不同 interface）。

### 13.5 联调顺序（严格按此顺序）

```text
① 只连腿臂，跑通 walk_control_V1 原有功能（确认没被改动影响）
② 只连 1 只手爪，设备地跑通 monitor → jog → seek-open → zero → move
```

## 14. 关键差异与已知坑

这一章是"别人踩过的坑"，值得在海报上贴一份。

### 14.1 CAN ID：文档写 `0x180`，代码是 `11`

- `资料/说明文档/README.md` 第 4 章、`docs/CAN_PROTOCOL.md`（章节标题）、`docs/INTEGRATION.md`、`host_demo/analyze_motion.py` 里还留着 **`0x180–0x184` / `0x080`** 这套旧 ID。
- **实际固件和 `claw_protocol.py` 用的是基址 11**（`CAN_ID_DEFAULT_BASE = 11`），命令帧 `0x00B`。
- 判据：**以固件基址 11 为准**，用 `candump -tz can0` 实测确认。看到 `00B`/`00C`/`00D` 就是对的。
- 如果你用 `candump -tz can0 | grep 180` 抓不到东西，不是设备坏了，是文档过时。

### 14.2 `max_pwm/startup_pwm` 组间不一致

- 组 1/3/4 = `100/100`，组 2 = `1000/600`。
- `README.md` 的共用表写 `1000/600`，只对组 2 成立。
- 症状："组 1 的手爪好像没劲/走不到目标"。先查 `params show` 里的 `max_pwm`。

### 14.3 组号 ≠ CAN 节点地址

- 组号只决定**板内用哪一行 PID/PWM 默认值**。
- 四块板可以是同一个组号也可以不同，CAN 上靠**物理总线**区分，不靠 ID。
- `params` 命令会校验文件组号和固件组号，不匹配直接拒绝——这是保护，不是 bug。

### 14.4 `grip` 不代表夹牢

- `grip` 是"按固定 PWM 推到头 + 保持"。
- `target_reached` 在 `grip` 下永远 0。
- 判断有没有夹住：看 `duty_permille` 是否到达 `hold_pwm`，以及物体有没有滑。

### 14.5 Hall 不是末端角度

- Hall 在减速箱输入侧，齿轮比 628.5:1（PG16M），所以**一个末端度 ≈ 大量 Hall 计数**。
- 断电、堵转、打滑都会让 Hall 与实际位置失配。失配后只能重新 `seek-open` + `zero`。
- 这也是为什么每次上电都要重建零点。

### 14.6 `zero` 不写 Flash

- 断电即丢。上位机程序必须自己实现"上电 → seek-open → 人工/自动确认 → zero"的流程。

### 14.7 `资料 copy/` 是 93 MB 的重复目录

- 与 `资料/` 内容完全相同，只是复制品。
- 建议：加进 `.gitignore`，或者直接删掉，避免以后改了一份忘了另一份。

### 14.8 电机手册 PDF 没有文字层

- `资料/手爪电机/ECU16024H12-S104-PG16M-0021.pdf` 是**单页图片**，无法提取文字。
- `鸣志官方.docx` 只有一行标题。
- 所以**本文不敢写电机的额定转矩/电流/转速**。需要这些参数请直接看 PDF 图片，或找厂家。
- 已知的只有：型号 `ECU16024H12-S104-PG16M-0021`、槽less BLDC、PG16M 减速箱、速比 **628.5:1**、1 对极。

### 14.9 没有电流环

- MS4931 的 SENSE 引脚没接到 ADC，**固件读不到电流，也做不了力矩控制**。
- 所有"力矩"只能靠 PWM 占空比近似。
- 所以堵转保护靠的是 **Hall 无变化 + 时间**（800 ms），不是电流检测。

### 14.10 端口/工具准备状态

- 本机**没装 `can-utils`** → `sudo apt install -y can-utils`。
- KH 模块**当前未插入** → `lsusb` 看不到 `0c72:0012`，`ip link` 没有 `can0`。所有实机步骤都要先插设备。
- `sudo` 在 snap 版 VS Code 的终端里不可用 → 请在**外部终端**执行带 `sudo` 的命令。

## 15. 故障排查表

| 现象 | 最可能原因 | 处理 |
|---|---|---|
| `candump` 一帧都没有 | 通道没 up / 波特率不对 / FD 开着 | `ip -details link show can0` 确认 `UP` + `1000000` + `fd off` |
| `candump` 一帧都没有，通道正常 | 板子没上电 / 12 V 没到 | 万用表量板载电源端子 |
| `candump` 一帧都没有，电源正常 | CANH/CANL 接反 / GND 没接 | 断电重接，三根都接 |
| `candump` 一帧都没有，接线正常 | 终端电阻缺失或过多 | 断电测 CANH–CANL，应约 60 Ω；U11 是否短接 |
| 有帧但 ID 不是 11–16 | 基址被改过 | `candump -tz can0` 全量看，找实际 ID，用对应 `--can-base` |
| `monitor` 报 `Errno 100`/`ENETDOWN` | 通道没 up | `sudo ip link set can0 up` |
| `monitor` 什么都不打印 | 用了错的 `--channel` 或 `--can-base` | 换通道试；确认基址 |
| 能 monitor，但 `jog` 不动 | 电机线 / Hall 线接错 | 看 `diagnostic hall` 是否变化；换 `--dir` 试 |
| `jog` 有一路 hall 不变 | 该路电机线或 Hall 线断/错 | 断电查 M?/HALL? 那一组线 |
| 动一下立刻停 | 心跳没发出去 / 500 ms 看门狗 | 检查上位机是否每 200 ms 发心跳 |
| `state=FAULT` | 故障锁存 | 先 `clear`，再 `monitor` 看 `fault` 位 |
| `result=RANGE` | 目标角度超 0–120° | 确认已 `zero`，且目标 ≤ 120 |
| `result=INVALID` | opcode/flags/CRC 错 | 用官方 CLI，别手搓帧 |
| 走到一半不动，`result=BUSY` | 运动中被新命令打断 / 参数写入被拒 | 等它停或 `stop` 后重试 |
| `target_reached=0` 但已经停了 | 位置环没收敛（`max_pwm` 太小 / 机械卡） | 查 `max_pwm`，查机械是否卡死 |
| `sync` 很大 / 报同步故障 | 三路机械不同步 / 某路打滑 | 重新 `seek-open` + `zero`；检查机械 |
| `grip` 之后物体滑脱 | `hold_pwm` 太小 | 逐步加 `hold_pwm`，同时监控温升 |
| 手爪动作方向反了 | DIR 极性 | `--dir` 换值；或改 `CLAW_SIGN_M?` 重新编译 |
| 参数改了没生效 | 写的是 RAM 但被重启清掉 | 重新 `load` 文件；每次上电都要加载 |
| `params load` 报组号不匹配 | 文件组号 ≠ 板子固件组号 | 用对应组的文件（`claw2_params.json` 只能给组 2） |
| 板子发烫 / 有异味 | PWM 太大 / 堵转 | 立刻断电；`hold_pwm`、`grip_pwm` 往下调 |
| 通信偶发丢帧 | 终端电阻数量不对 / 线太长 / 没双绞 | 检查终端；缩短线；CANH/CANL 双绞 |
