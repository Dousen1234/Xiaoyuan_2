## 1. 这个界面是干什么的

`x3588_ui` 是一个跑在 3588 上的 Qt5 窗口程序，把原来要开好几个终端、手敲一堆命令的操作全部收到一个窗口里：

| 功能 | 对应原来要手敲的东西 |
|---|---|
| ① 鲲弘 CAN 接口 can0～can5 拉起并设置波特率 | `kcanctl up can0 1000000` 或三条 `ip link` |
| ② 3588 片上 CAN 接口 `can_mcu` 拉起并设置波特率 | 同上 |
| ③ 指定上位机读取的轨迹 xlsx 路径与名称 | `upper_control --xlsx /path/xxx.xlsx` |
| ④ 分别启动 / 停止下位机、上位机程序 | 两个终端分别跑 `lower_control`、`upper_control` |
| ⑤ 调用回 0 位工具（选腿 + 指定时长） | `leg_goto_zero --leg A --time 8 --auto` |
| ⑥ 电机状态反馈栏（16 关节实时角度 / 在线 / 帧数） | 原本没有，只能看日志猜 |
| ⑦ CAN 总线状态面板（UP/DOWN、波特率、错误计数） | `ip -details link show` |
| ⑧ 运行日志（4 个标签页） | 各终端自己滚屏 |
| ⑨ 全局急停 | 下位机 `estop` + 广播停止帧 + 杀掉上位机 |

**这个程序本身不做运动学计算、不发轨迹。** 它是个"遥控器 + 监控面板"，实际的运动由 `lower_control`（下位机）和 `upper_control`（上位机）完成，界面只负责把它们启动起来、把参数传进去、把输出显示出来。

### 为什么需要一个专门的 sudo 启动脚本

配置 CAN 接口（`ip link set ... type can bitrate ...`）必须是 root。但 3588 上的图形界面是普通用户 `rk` 在 `DISPLAY=:1` 上跑的，root 直接 `sudo ./build/x3588_ui` 会因为读不到 X 授权文件（`/run/user/1000/gdm/Xauthority` 权限是 `-rwx------`）而报"无法连接到显示"。

所以流程是：

```
你在终端里执行一次  sudo ./run_ui_sudo.sh   ← 这里输一次密码
        ↓
脚本把 X 授权文件复制一份给 root、设好 DISPLAY，再 exec 界面
        ↓
界面以 root 身份运行 → 界面里所有操作都不再需要密码
```

## 2. 安装与编译

### 2.1 安装 Qt5 开发包（只需一次）

```bash
sudo apt update
sudo apt install -y qtbase5-dev
```

验证：

```bash
dpkg -l | grep qtbase5-dev
```

### 2.2 编译

```bash
cd /home/rk/walk_systemctl/workspaces/Xiaoyuan_2/3588_control
mkdir -p build && cd build
cmake ..
make -j4
```

`cmake` 结束时会打印一行：

```
--   图形界面    : .../3588_control/build/x3588_ui
--               （用 sudo ./run_ui_sudo.sh 启动）
```

如果**没有**打印这一行，而是打印了：

```
--   未找到 Qt5 Widgets，跳过 x3588_ui（apt install qtbase5-dev 后可编译）

## 3. 启动方式（重点：sudo 只输一次密码）

### 3.1 正确启动方式（唯一推荐）

```bash
cd /home/rk/walk_systemctl/workspaces/Xiaoyuan_2/3588_control
sudo ./run_ui_sudo.sh
```

终端会提示输入密码，**输入一次**，界面就起来了。之后在界面里点任何按钮（包括拉起 CAN、启停程序）都不会再问密码。

### 3.2 为什么不能直接 `sudo ./build/x3588_ui`

| 现象 | 原因 |
|---|---|
| `qt.qpa.xcb: could not connect to display` | root 拿不到 `DISPLAY` 环境变量 |
| `Authorization required, but no authorization protocol specified` | 读不到 `Xauthority` |
| 界面能起但中文全是方块 | root 的字体配置与 `rk` 用户不同 |

`run_ui_sudo.sh` 帮你做了四件事：

1. 把 `rk` 用户的 X 授权文件复制到 `/tmp/.x3588_ui_xauth.1000`（权限 600）并 `export XAUTHORITY`
2. 自动探测显示号（先试 `:1`，再试 `:0`）
3. 把 `HOME` / `USER` / `LOGNAME` 切回 `rk`，这样字体、配置、用户目录都对
4. 清掉 snap 那套会破坏 Qt 的环境变量（`GTK_PATH`、`LD_LIBRARY_PATH` 等）

### 3.3 脚本源码与可调项

脚本位置：`3588_control/run_ui_sudo.sh`，几个可调点：

| 变量/行为 | 说明 |
|---|---|
| `TARGET_UID` / `TARGET_USER` | 默认从 `SUDO_UID` / `SUDO_USER` 取，取不到就退回 `1000` / `rk` |
| `TARGET_HOME` | 由 `getent passwd` 查，查不到退回 `/home/$TARGET_USER` |
| X 授权搜索顺序 | `/run/user/$UID/gdm/Xauthority` → `/run/user/$UID/Xauthority` → `$HOME/.Xauthority` |
| 显示号搜索顺序 | 沿用已有 `DISPLAY`；否则 `:1` → `:0` |
| 可执行文件搜索顺序 | `build/x3588_ui` → `x3588_ui` → `build/bin/x3588_ui` |

### 3.4 非 root 启动（只能看，不能改）

只想知道界面长什么样、想看看关节反馈，可以：

```bash
./build/x3588_ui
```

这时：
- ✅ 能打开界面、看日志、看电机表、看总线状态
- ❌ 点【应用配置】会弹"需要 root 权限"
- ✅ CAN 监控线程仍能正常工作（非 root 打开 `AF_CAN` socket 是允许的，已验证）

### 3.5 退出

直接关窗口。如果下位机 / 上位机 / 回零还在跑，会先弹确认框：

> 有程序仍在运行，是否全部停止并退出？

选"否"取消退出。选"是"会：
1. 给下位机发 `requestStopAll()`（广播 0x02 停止帧）
2. 等 120 ms
3. 关监控 socket
4. 依次对 上位机 / 回零 / 下位机 `terminate()`，等 2500 ms，不行再 `kill()`

## 5. 七个功能区逐一说明

### ① CAN 接口配置

**位置**：左上角。

**7 行通道**：`can0` `can1` `can2` `can3` `can4` `can5` `can_mcu`，每行四件套：

| 控件 | 含义 |
|---|---|
| ☑ 勾选框 | 是否参与"应用配置" |
| 通道名 | 接口名（如 `can0`） |
| **物理端口**（只读） | 该接口名**实际绑定到哪个物理插口**，直接读 sysfs 得出 |
| 波特率输入框 | 单位 bit/s，范围 10000～2000000，步长 10000，带千分位显示 |
| 状态标签（只读） | 从 `ip -details -json link show` 解析出来的实时状态 |

**默认勾选**：`can0` `can1` `can2` `can3` `can5`
**默认不勾**：`can4`（未接线）、`can_mcu`（避免和自带的监控线程抢）

> ### ⚠️ 一定要看【物理端口】这一列
>
> `can0`~`can5` 这个**接口名不等于物理插口序号**。
>
> kcan 驱动是按**枚举顺序"抢空位"**命名，不是按 USB 口编号命名。实测的枚举过程是：
>
> 1. 板载 CAN（`fea60000.can`）先枚举，抢到 `can0`
> 2. USB 口 1~4 依次拿到 `can1` `can2` `can3` `can4`
> 3. `10-can-mcu.link` 把板载 CAN 改名成 `can_mcu`，**`can0` 空出来了**
> 4. USB 口 **5** 紧接着枚举，抢到这个刚空出来的 `can0`
> 5. USB 口 6 拿到 `can5`
>
> 结果就是：**`can0` 实际是第 5 个 USB 口（`2-1.4.2.5`）**，而不是第 1 个。
>
> | 接口名 | 实际物理口 |
> |---|---|
> | `can0` | USB `2-1.4.2.5`（**第 5 口**） |
> | `can1` | USB `2-1.4.2.1`（第 1 口） |
> | `can2` | USB `2-1.4.2.2` |
> | `can3` | USB `2-1.4.2.3` |
> | `can4` | USB `2-1.4.2.4` |
> | `can5` | USB `2-1.4.2.6`（第 6 口） |
> | `can_mcu` | 板载 `fea60000.can` |
>
> **这个映射每次重启、每次插拔 USB 都可能变**（枚举顺序不保证）。
>
> 想让 `can0` 真正对应第 1 个物理口，请在 3588 上执行一次（需要 root）：
>
> ```bash
> cd /home/rk/walk_systemctl/workspaces/Xiaoyuan_2/3588_control/deploy
> sudo ./install_kcan_persistent_name.sh
> ```
>
> 装完用（**不需要 root**）核对：
>
> ```bash
> ./install_kcan_persistent_name.sh --check
> ```
>
> 全部 `[ OK ]` 就说明命名已固定。详见 `deploy/60-kcan-persistent-name.link` 里的完整说明。
>
> ⚠️ 重新枚举后各通道的**波特率和 up 状态会丢失**，需要在界面里重新勾选 + 点【应用配置】。

**默认波特率**：

| 通道 | 默认值 | 说明 |
|---|---|---|
| `can0` `can1` `can2` `can3` | **1000000**（1 Mbps） | 腿臂电机，鲲弘 |
| `can5` | **990000** | 下位机侧（鲲弘 kcan），实测采样点 0.740 |
| `can_mcu` | **990000** | 上位机侧（rockchip_canfd），实测采样点 0.740 |
| `can4` | 1000000 | 未接线，默认不勾 |

> **注意**：`can5` 和 `can_mcu` 必须波特率一致，否则上位机 ↔ 下位机的链路直接 ERROR-PASSIVE。990000 是这套硬件实测能稳跑的值，不要随意改成 1000000。

**三个按钮**：

| 按钮 | 实际执行 |
|---|---|
| 应用配置（up + 设置波特率） | 对每个勾选的通道：先试 `kcanctl up <通道> <波特率>`；失败则退回三条 `ip link ` 命令（`set X down` → `set X type can bitrate N` → `set X up`）。完成后自动刷新状态 |
| 关闭全部 | 逐条 `ip link set <通道> down`。**会先弹确认框**，并且会先关掉 CAN 监控（否则 socket 会报错） |
| 刷新状态 | 立即执行一次 `ip -details -json link show` 并更新所有状态标签 |

**状态标签颜色**：

| 显示 | 颜色 | 含义 |
|---|---|---|
| `UP 1000000` | 绿 | 正常 |
| `DOWN` | 灰 | 未拉起 |
| `—` | 灰 | 若接口不存在 |
| 其他异常 | 红 | 解析失败 |

### ② （与 ① 同区）——`can_mcu` 的关键约定

这一条单独拿出来说，因为它是**最容易踩的坑**。

`can_mcu`、`upper_control`、`leg_goto_zero` 三者都想打开同一个 CAN 口。界面用"自动退让"策略解决：

| 场景 | 界面的行为 |
|---|---|
| 平时（只开界面） | 界面独占 `can_mcu`，每 200 ms 轮询一次 16 个关节的 `0x41` 状态帧 → 填充电机表 |
| 启动上位机 | 界面**自动停止主动轮询**（`setActivePolling(false)`），只被动监听，把带宽让给 `upper_control` |
| 停止上位机 | 界面**自动恢复主动轮询** |
| 开始回零 | 界面**完全关闭** `can_mcu`（`stop()`），因为 `leg_goto_zero` 需要独占 |
| 回零结束 / 中止 | 界面**自动重新打开** `can_mcu` |
| 回零过程中关掉监控 | 记一个 `m_monitorPausedForGoto` 标志，回零结束时不会强行打开 |

所以：**你不需要手动开关监控，界面会自己让路。** 如果看到顶栏"CAN 监控：已暂停（回零中）"，那是正常现象。

### ③ 上位机轨迹文件

**位置**：右上角上半。

| 控件 | 说明 |
|---|---|
| 路径输入框 | 手输完整路径。**默认留空**（避免误发上一次的旧轨迹）；占位提示会提示未选择，并给出示例路径 `.../step_position/step_test_ui.xlsx` |
| 浏览… | 打开文件选择框，过滤器是 `Excel 工作簿 (*.xlsx);;所有文件 (*)`；路径为空时从用户主目录开始 |
| 频率 | 1～100 Hz，默认 **10 Hz**，后缀 ` Hz`。透传为 `upper_control --hz` |
| 循环次数 | 0～9999，默认 **1**。特殊值文本"0（无限）"。透传为 `upper_control --loop` |

**校验**：点【启动】时会先检查路径是否为空、文件是否存在，任一不满足就弹框提醒，不会把进程起起来。

### ④ 上 / 下位机程序

**位置**：左上角下半，分成两个 group。

#### 下位机 group

| 按钮 | 实际动作 |
|---|---|
| 启动 | 找到 `<程序目录>/lower_control`，确认可执行，`setWorkingDirectory(程序目录)`，启动 |
| 停止 | 先写 `quit\n` 到它 stdin 并 `closeWriteChannel()`，等 4 s，不行 `terminate()`，再不行 `kill()` |
| `arm 解抱闸` | 往下位机 stdin 写 `arm all\n` |
| `disarm 抱闸` | 往下位机 stdin 写 `disarm all\n` |
| `resume 解除急停` | 往下位机 stdin 写 `resume\n` |
| `stat 打印状态` | 往下位机 stdin 写 `stat\n`，输出会出现在【下位机】日志页 |

状态标签会显示 `● 运行中 (PID 12345)` 或 `● 未运行`。

#### 上位机 group

| 按钮 | 实际动作 |
|---|---|
| 启动 | 校验 xlsx → 如果下位机没在跑会弹"仍要继续吗" → 拼参数 `--can <接口> --hz <N> --xlsx <路径> --auto --loop <N>` → 先把监控切成被动 → 启动 |
| 停止 | `terminate()` → 等 3 s → `kill()` → 恢复监控主动轮询 |

> **为什么必须是 `--auto`**：`upper_control` 检测到 stdin 不是终端（被 QProcess 接管）时会跳过文件选择器，直接用 `--xlsx` 指定的文件。不加 `--auto` 在有终端时反而会弹交互菜单。

### ⑤ 回 0 位

**位置**：右上角下半。

| 控件 | 说明 |
|---|---|
| 腿下拉框 | `A 腿` / `B 腿` / `C 腿` / `D 腿` |
| 时长输入 | 0.5～600.0 秒，1 位小数，步长 0.5，默认 **8.0 秒**，后缀 ` 秒` |
| 开始回零 | 弹确认框（显示腿别、时长、目标 0.00°）→ 关掉 CAN 监控 → 拼 `--leg <X> --time <S> --can <接口> --auto` → 启动 |
| 中止 | 弹确认框 → `terminate()` → 等 3 s → `kill()` |

上方有一行提示：说明回零走五次多项式、会自动释放 `can_mcu`。

下方有一行橙色提示：**C 腿和 D 腿的电机挂在 can2 / can3 上，必须先让 can2 / can3 变成 UP，否则回零会报链路错误。**

**回零结束后的自动行为**：连接了 `finished` 信号，回零正常结束或中止后会自动重新打开 CAN 监控。

### ⑥ 电机状态反馈

**位置**：中部左侧。

`QTableWidget`，16 行 × 7 列：

| 列 | 内容 |
|---|---|
| 关节 | `A1` `A2` `A3` `A4` … `D4`（等宽字体） |
| 在线 | `在线`（绿）/ `离线`（灰）/ `—`（监控未开） |
| 实际角(°) | `%.2f`，来自下位机上报的 `0x41` 状态帧 |
| 目标角(°) | 预留列 |
| 误差(°) | 预留列 |
| 帧数 | 该关节收到的状态帧累计数 |
| 限位 | 预先填好的软限位范围，超出时变红并加 `⚠超限` |

**各关节软限位**（`kLimDeg`）：

| 关节 | 限位 |
|---|---|
| J1 | −120 ～ +120 |
| J2 | −120 ～ +120 |
| J3 | **−60 ～ +180** |
| J4 | −90 ～ +90 |

刷新周期 **150 ms**。如果 CAN 监控没打开，在线列全显示 `—`，实际角也显示 `—`。

### ⑦ CAN 总线状态面板

**位置**：中部右侧。

`QTableWidget`，4 列：`通道` `状态` `波特率` `错误计数`。

数据来源：`ip -details -json link show` 的输出。解析规则：

- **以 `operstate` 判断 UP/DOWN**（不能用 `flags` 里有没有 `"UP"`，`eth0` 就有 `flags:["UP"]` 但 `operstate:"DOWN"`，会误判）
- `bitrate` 取 `linkinfo.info_data.bittiming.bitrate`
- `state` 取 `linkinfo.info_data.state`，`ERROR-ACTIVE` 是健康状态
- 错误计数取 `berr_counter.tx` / `berr_counter.rx`

刷新周期 **1500 ms**，也可以点【立即刷新】。

面板下方有一行小字，显示当前 `ip -details -json` 的用法提示；右下角还有一个 `Tx N / Rx N` 帧计数（界面自己发的 / 收的）。

### ⑧ 运行日志

**位置**：下部。

`QTabWidget` 四个标签页，每个标签页是一个 `QPlainTextEdit`（等宽 9 pt，不自动换行，最多保留 5000 段，超出滚掉最老的）：

| 标签页 | 内容 |
|---|---|
| 系统消息 | 带 `[HH:mm:ss]` 前缀的界面自己的操作记录，同时会在状态栏闪 6 s |
| 下位机 | `lower_control` 的 stdout + stderr（合并通道） |
| 上位机 | `upper_control` 的 stdout + stderr |
| 回零 | `leg_goto_zero` 的 stdout + stderr |

日志是**实时**的（`QProcess::readyReadStandardOutput` 信号驱动），每启动一个程序，开头会打一行 `=== [xxx] 启动 ===` 加完整命令行，方便回看当时到底传了什么参数。

自动滚动策略：只有当滚动条本来就在最底部时才自动跟着滚。你想往上翻看历史，它就不会抢你的位置。

### ⑨ 全局急停（红色的那个）

**位置**：顶栏最右，120×40，红底白字，特别显眼。

点它会**同时**做四件事：

1. 如果下位机在跑 → 写 `estop\n` 到它 stdin
2. 无条件通过 CAN 广播 `0x02` 停止帧给 16 个关节 ID（`requestStopAll()`）
3. `terminate()` 上位机进程
4. `terminate()` 回零进程

然后在状态栏显示 60 s 的提示，并弹一个信息框说明**恢复步骤**：

```
1. 确认现场安全
2. 点【resume 解除急停】
3. 点【arm 解抱闸】
```

> 急停按钮**不需要任何前置条件**，任何时候都可以点。它的设计原则是"能停就停，停不了也至少把停止帧发出去"。

## 6. 典型操作流程（重启后从零到发轨迹）

### 第 0 步：确认硬件

- 上下位机 CAN 线（H/L）物理连接好，两端终端电阻 120 Ω 已装
- 四条腿臂的 can0～can3 接线到位
- 关节电源已上电

### 第 1 步：拉起界面

```bash
cd /home/rk/walk_systemctl/workspaces/Xiaoyuan_2/3588_control
sudo ./run_ui_sudo.sh
```

### 第 2 步：拉起 CAN 接口

1. 在【① CAN 接口配置】里确认勾选：`can0` `can1` `can2` `can3` `can5`
2. 确认波特率：`can0~3` = `1000000`，`can5` = `990000`
3. 点【应用配置（up + 设置波特率）】
4. 看状态标签是否都变成绿色的 `UP ...`；不绿就点【刷新状态】再看
5. 如果 `can_mcu` 需要单独拉起（一般界面会自动处理），手动勾上再点一次应用

### 第 3 步：启动下位机

1. 在【④ 上下位机程序 → 下位机】点【启动】
2. 切到【⑧ 运行日志 → 下位机】标签页，确认打印了初始化日志
3. 点【stat 打印状态】，确认 16 个关节都能读到

### 第 4 步：解抱闸

点【arm 解抱闸】，日志里应该能看到抱闸释放的回读。

### 第 5 步（可选）：先回零

1. 【⑤ 回 0 位】：选腿（例如 `A 腿`），时长填 `8.0`
2. 点【开始回零】，确认弹框
3. 看【⑧ 运行日志 → 回零】观察轨迹执行
4. 结束后监控会自动恢复，【⑥ 电机状态反馈】里 A 腿 4 个关节角度应接近 0

### 第 6 步：填轨迹文件

1. 【③ 上位机轨迹文件】点【浏览…】选 xlsx，或直接手输路径
2. 频率填 `10`，循环次数填 `1`（`0` = 无限）
3. 可以先在命令行跑一次 `upper_control --xlsx <路径> --list-sheets` 确认 sheet 名

### 第 7 步：启动上位机

点【④ → 上位机 → 启动】。如果下位机没在跑会弹提醒。

此时界面会自动把 CAN 监控切成被动模式（顶栏显示"CAN 监控：已打开（被动监听）"）。

### 第 8 步：观察

- 【⑧ → 上位机】看发送日志
- 【⑥ 电机状态反馈】看实际角度变化、帧数是否在涨
- 【⑦ CAN 总线状态】看 `错误计数` 是否在涨（涨得厉害说明接线 / 终端电阻 / 波特率有问题）

### 第 9 步：收尾

1. 【④ → 上位机 → 停止】
2. 【④ → 下位机 → disarm 抱闸】
3. 【④ → 下位机 → 停止】
4. 【① → 关闭全部】（可选，会先弹确认框）
5. 关窗口

## 7. 故障排查表

### 7.1 界面打不开

| 现象 | 原因 | 处理 |
|---|---|---|
| `qt.qpa.xcb: could not connect to display` | 没用脚本启动，或脚本探测显示号失败 | 用 `sudo ./run_ui_sudo.sh`；若仍失败，先 `echo $DISPLAY` 看当前用户的显示号，再 `sudo DISPLAY=:1 ./run_ui_sudo.sh` |
| `Authorization required, but no authorization protocol specified` | X 授权文件没读到 | 确认 `/run/user/1000/gdm/Xauthority` 存在；脚本会自动复制到 `/tmp/.x3588_ui_xauth.1000` |
| 窗口起来但超出屏幕 | 老版本没做高度限制 | 当前版本窗口 1700×1000，屏幕 1920×1080，正常不会溢出 |
| **字太小看不清** | **老版本用了默认字号** | **本版本已整体放大：波特率 12pt 加粗、运行状态 13pt、表格 11pt 行高 27px，见 §4.1** |
| 中文全是方块 | 字体没找到 | 程序启动会打印 `使用字体：xxx`，正常应为 `Noto Sans CJK SC`；缺字体时 `sudo apt install fonts-noto-cjk` |
| `Permission denied` | 脚本没有可执行位 | `chmod +x run_ui_sudo.sh` |
| 编译时提示"未找到 Qt5 Widgets" | 缺 `qtbase5-dev` | `sudo apt install -y qtbase5-dev` |

### 7.2 CAN 配置失败

| 现象 | 原因 | 处理 |
|---|---|---|
| 点【应用配置】弹"需要 root 权限" | 非 root 启动 | 用 `sudo ./run_ui_sudo.sh` |
| 状态标签一直 `DOWN` | 接口被别的进程占用 / 硬件不支持 | 终端手动试 `sudo ip link set can0 down; sudo ip link set can0 type can bitrate 1000000; sudo ip link set can0 up`，看具体报错 |
| 报 `RTNETLINK answers: Device or resource busy` | 有程序正在用这个口 | 先【关闭全部】，再重新应用 |
| `can2` / `can3` 起不来 | 这两路需要单独确认硬件支持 | 见 7.5 |

### 7.3 关节全部离线

| 检查顺序 | 动作 |
|---|---|
| 1 | 顶栏"CAN 监控"是不是显示"已关闭"→ 点【打开 CAN 监控】 |
| 2 | 【⑦ CAN 总线状态】里 `can_mcu` 是不是 `UP` |
| 3 | 下位机有没有在跑（【④ 下位机】状态标签） |
| 4 | 下位机有没有 arm 解抱闸 |
| 5 | 【⑧ → 下位机】日志里有没有关节通信超时 |

### 7.4 心跳无响应（顶栏红色"心跳：无响应"）

| 原因 | 处理 |
|---|---|
| 下位机没启动 | 启动下位机 |
| `can5` / `can_mcu` 波特率不一致 | 两边都设成 990000 |
| CAN 线没接 / 终端电阻缺失 | 检查物理连接 |

### 7.5 C 腿 / D 腿回零失败

**原因**：C 腿挂在 `can2`，D 腿挂在 `can3`，而这两路在默认状态下是 `DOWN`。

**处理**（需要你自己在终端执行，界面里点【应用配置】也可以，但要先勾上 can2 / can3）：

```bash
sudo ip link set can2 type can bitrate 1000000
sudo ip link set can2 up
sudo ip link set can3 type can bitrate 1000000
sudo ip link set can3 up
```

然后在界面里【刷新状态】确认变绿。

### 7.6 软限位报警（顶栏橙色"限位：关节X 上限/下限"）

| 含义 | 处理 |
|---|---|
| 某个关节撞到软限位，下位机已锁死 | 先点顶栏【清限位】（此时橙色按钮亮起）解除锁定 → 再把该关节手动移回安全范围 |
| 报警不消失 | 点【清限位】（在顶栏，和急停同一行，橙色按钮）；若按钮置灰，说明没打开 CAN 监控，无法得知报警状态，先点【打开 CAN 监控】 |

> **【清限位】按钮行为**
>
> - **仅在检测到下位机软限位锁定时可用**（按钮变橙、带红色描边）；无报警或未开 CAN 监控时置灰不可点。
> - 点击后同时做两件事：向下位机终端写入 `clear`，并在 `can5` 上广播 `0x03`（互为兜底）。
> - **清除后不会让关节自己动**。触限关节必须先退回限位内 **≥2.0°**（回滞保护），才会重新接收目标角。
> - 对应哈希命令：`lower_control` 里敲 `clear`，或任意程序在总线上发 `[0x03]`（DLC=1）。

### 7.7 上位机启动后日志刷 ERROR-PASSIVE

| 原因 | 处理 |
|---|---|
| 波特率不匹配 | `can5` 与 `can_mcu` 必须相同 |
| 上位机比下位机先起 | 先起下位机，再起上位机 |
| 没有下位机在线（心跳为 0） | 等心跳正常再起上位机 |

## 9. 安全须知

1. **急停按钮随时可用，但它不是安全回路。** 它发的是 CAN 停止帧和进程终止信号，不是硬件断电。真正的安全依赖急停开关 / 断电。
2. **`lower_control` 的 `arm` 会解抱闸。** 解闸之后如果地面不平、或者腿没支撑好，腿会直接掉下去。解闸前确认腿已落地或有支撑。
3. **`leg_goto_zero` 会让关节实际运动。** 回零前确认该腿周围无人、无障碍。
4. **急停后恢复顺序固定**：`resume` → `arm`。顺序反了不会生效。
5. **C / D 腿依赖 can2 / can3 是 UP 状态**，否则回零会直接报链路错误，或者在运动中掉线。
6. **不要在回零过程中关掉窗口**。虽然会弹确认框，但强杀 `leg_goto_zero` 会让关节停在最后一个目标位置（不会失控，但也不是 0 位）。
7. **关闭窗口时会发停止帧 + 杀掉三个子进程**，但如果是 `kill -9` 强杀界面本身，子进程会变成孤儿继续跑。这时需要手动 `pkill lower_control`。
8. **界面以 root 运行**。这意味着界面里启动的所有子进程也是 root。不要在这个界面里做与运动无关的 root 操作。

## 附：内部实现要点（给维护者看）

### 线程模型

```
主线程 (Qt event loop)
├── QProcess × 3       lower_control / upper_control / leg_goto_zero
├── QTimer 500 ms      tickProcesses()     进程状态 + 监控模式仲裁 + 顶栏标签
├── QTimer 150 ms      tickMotorTable()    电机表刷新
└── QTimer 1500 ms     tickBusStatus()     ip -details -json 解析

CanMonitor 工作线程（std::thread）
└── 200 ms 轮询 0x41 状态帧 / 被动接收 0x161 心跳、0x162 限位报警
    ├── 主动模式：按需发 0x41 查询
    └── 被动模式：只收不发（上位机在跑时）
```

### `can_mcu` 占用仲裁（`tickProcesses`）

```cpp
const bool upperRun = (m_upper->state() != QProcess::NotRunning);
if (m_mon && m_mon->isOpen() && !m_monitorPausedForGoto)
{
    const bool wantActive = !upperRun;
    if (m_mon->activePolling() != wantActive)
        m_mon->setActivePolling(wantActive);
}
```

这一句保证了帧率冲突不会发生。

### 数据来源

| 数据 | 来源 |
|---|---|
| 关节实际角 | CAN `0x41` 状态帧，`data[1..4]` 是小端 int32，除以 `kAngleScale=10000` 得弧度 |
| 关节在线 | 最近一次收到该 ID 的 `0x41` 帧时间距今 < 阈值 |
| 心跳 | `0x161` 心跳帧，`data[0]` 是位标志：bit0 流模式、bit1 在线、bit2 限位锁定 |
| 限位报警 | `0x162` 报警帧，`data[0]==0x62`，`data[1]` 是关节 ID，`data[2]` 是 1=上限 / 2=下限 |
| 接口状态 | `ip -details -json link show` |
